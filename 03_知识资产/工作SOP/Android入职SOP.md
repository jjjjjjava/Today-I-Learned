# Android 入职 SOP

## 第一部分：第一天

### 1. 报到、认识人

- [ ] 完成手续，加入工作群；认识 leader、mentor、邻桌。
- [ ] 问 mentor：“咱们平时一般怎么称呼 leader？”与 leader 打招呼、听安排。

**自我介绍：**
> 大家好，我是今天新入职的 Android 开发潘锐琦，大家叫我小潘就好了，很高兴加入咱们团队，以后工作中还请大家多多关照。

**邻桌：**
> 哎，你好，我是 Android 组新来的，我叫小潘，以后就是同事了，请问你怎么称呼？

对方回答后，按团队习惯称呼：“李阳，认识了，你先忙，我就不打扰了。”

**Leader：简单介绍自己，表达来报到。**

称呼先问 mentor，下面用“阳哥”举例：

> 阳哥好，我是今天新来的 Android 开发潘锐琦，叫我小潘就行，过来跟您打个招呼。

对方聊就接着聊；对方忙就说：

> 那您先忙，我先找 mentor 熟悉一下环境。

**Mentor：介绍自己，自然接到后续配合。**

> 李哥好，我是今天新来的小潘，阳哥说后面让您带我。我先过来认个人，之后工作上还得多跟您请教。

接着问：

> 您看我今天先从哪儿开始？有没有新人文档，我先看看？

不用背整段。称呼跟团队习惯；“哥”和“您”不顺口就换成名字和“你”。重点是自然介绍、给对方接话空间。

### 2. 午餐

> 哥，咱们公司附近哪边吃饭比较方便啊，你们等会去点外卖还是去食堂吃？我刚来还不太认识路。

### 3. 向 mentor 问开发流程

> 新人文档、环境配置说明在哪里看？我想了解下咱们从接需求到上线的流程。

文档已有说明的跳过，重点补问缺项：

- [ ] **接需求**：任务在哪看、谁分配？需求疑问找谁？
- [ ] **需求评审**：什么时候参加？排期怎么给、谁确认？
- [ ] **技术方案**：什么需求要写？有模板吗？谁评审？
- [ ] **开发规范**：分支、提交、代码风格有什么要求？
- [ ] **代码 Review**：谁审？提测前还是合并前？合并条件是什么？
- [ ] **自测**：必测场景、机型有哪些？单元测试和 UI 自动化有什么要求？
- [ ] **提测**：怎么打包、提交测试？提测说明写什么？
- [ ] **上线**：谁合并、谁发布？开发跟进哪些线上指标？

### 4. 权限与环境

- [ ] 申请代码、文档、任务和构建平台权限；确认 Android Studio、JDK、SDK、构建配置及测试设备。
- [ ] 问 mentor：公司允许哪些 AI 工具？账号和项目代码使用有什么规定？
- [ ] 明后天配置 AI 环境、尝试跑通代码；优先保证项目能编译、运行、调试。

AI 候选清单：Codex、skill、caveman、skill-manager、grill-me、Cockpit Tools，按需配置。

### 5. 当天收尾

- [ ] **记录**：人员职责与称呼、文档入口、流程要点、权限与环境状态、阻塞及跟进人。
- [ ] **补 Wiki**：向 mentor 确认位置和提交要求，尽量补充已验证的配置步骤、问题解决方法。
- [ ] **私聊 leader**：按实际情况汇报完成事项、阻塞和下一步。

> 今天主要完成了入职手续，了解了公司的规章制度和基本开发流程。明后天计划配置 AI 相关环境，并尝试跑通项目代码。

有阻塞则补一句：“目前代码仓库权限还在申请，已找对应负责人跟进。”

## 第二部分：长期执行

### 1. 接任务时：确认范围与安排

- [ ] 找产品经理确认范围、交互和验收标准；找任务负责人或 leader 确认优先级、排期；找协作同事确认接口和联调依赖。
- [ ] 先评估实现和依赖，再承诺提测时间。
- [ ] 私聊澄清问题，需求单记录最终结论；变更影响多人时，在对应需求群同步。已有明确说明的内容不重复确认。

> 我梳理了下，这次做 A、B，C 暂时不做；异常情况按 D 处理，我理解对吗？我先看下实现和接口依赖，再同步预计提测时间。

### 2. 卡住时：及时求助与同步风险

- [ ] 先查文档、自己尝试；提问说明目标、卡点、已尝试的方法，附必要日志或截图。
- [ ] 说明对交付的影响、需要的帮助和跟进人；可能影响排期时及时同步，不等周报。

> X 卡在 Y，已尝试 A、B，目前发现 Z。可能影响周四提测，需要协助确认 C；我会先推进不依赖它的部分。

### 3. 每周：简短汇报

- [ ] 按团队已有渠道和节奏提交；尚无安排时，与 leader 确认汇报方式。
- [ ] 只写四项：完成结果、当前风险、下周计划、需要支持；关键成果附任务、PR 或 Wiki 链接。

```text
本周结果：X 已提测／上线，验证结果……（链接）
当前风险：……；处理进展……；预计影响……
下周计划：……；预计完成时间……
需要支持：……（没有则省略）
```

### 4. 有成果时：记录、展示、复用

- [ ] 随手记录：问题、自己的行动、验证结果、证据链接；说明同事贡献。
- [ ] 周报提炼一句结果，链接指向详细记录；转正时按交付、质量、效率等价值汇总，重点讲主要贡献。
- [ ] 优化先确认实际价值和修改范围；没有实测数据，不声称性能提升，不为凑成果改无关代码。

**记录示例：**

> 开发 X 需求时，移除 Y 页面无独立作用的一层容器，布局由 N 层减至 N−1 层，相关展示和交互验证通过。PR：链接。暂未验证性能收益。

**周报摘要：**

> X 需求已提测；同时简化 Y 页面一层冗余布局，相关场景验证通过（PR 链接）。

小优化作为支撑案例；主要交付作为转正材料重点。同一条记录持续复用，不重复写多套材料。

### 5. 交付后：跟进到完成

- [ ] 跟进代码 Review、自测、提测和缺陷修复，按团队标准确认验收。
- [ ] 确认发布安排和负责人；上线后检查相关功能与线上指标，发现异常及时处理或同步。
- [ ] 更新任务状态，补充必要文档和结果链接。

### 6. 阶段节点：确认预期与改进方向

- [ ] 初期向 mentor 了解培养计划和考核材料，再与 leader 确认试用期目标、验收标准及反馈节点。
- [ ] 在约定节点带着交付结果沟通，记录改进项与下一次检查时间。

> 目前我完成了 A、B，接下来准备做 C。现在的交付符合预期吗？下一阶段最需要补哪一项？

日常协作：承诺有回应、变更提前说、求助带信息、贡献如实说明。不要求每天私聊汇报、每件小事留痕或每周必须做优化。
